# Portal sync agent

The PideInfo agent is a standalone Python application that runs on the user's local machine. It authenticates against Spain's Portal de Transparencia using the user's FNMT digital certificate, scrapes their FOIA request data (expedientes and notifications), downloads documents, and forwards everything to PideInfo via webhook.

## Architecture overview

```
User's machine                             PideInfo server
──────────────                             ───────────────
PideInfo Agent (Python)
  │
  ├── Playwright (headed browser)
  │   └── Cl@ve + FNMT certificate ──→ Portal de Transparencia
  │       └── Returns session cookies
  │
  ├── httpx (async HTTP)
  │   ├── GET /privada/expedientes
  │   ├── GET /privada/notificaciones
  │   └── GET /.rest/download/v1/descargaDocumento
  │
  └── POST /api/agent/webhook ─────────→ AgentApiController
      (Authorization: Bearer <JWT>)         ├── AgentWebhookProcessor
                                            ├── Deduplicates by SHA-256
                                            ├── Stores in S3
                                            └── Dispatches ProcessDocumentBatchMessage
                                                    │
                                                    ▼
                                            AI pipeline (same as manual uploads)
```

The agent is intentionally thin — it only downloads and forwards. All document intelligence (AI classification, request matching, state transitions) stays in PideInfo's PHP backend.

## Authentication with PideInfo

The agent authenticates against PideInfo using a JWT token generated by the user from the web interface. This replaces the previous shared-secret model.

### Token generation flow

1. User logs into PideInfo web, opens the user dropdown, clicks **Conectar agente**
2. A modal appears with a **Generar token** button
3. Backend generates a JWT signed with the app's private key (`config/jwt/private.pem`) via `lexik/jwt-authentication-bundle`
4. Token is displayed once — the user copies it
5. Token validity: 1 year (`token_ttl: 31536000` in `config/packages/lexik_jwt_authentication.yaml`)

Backend endpoint: `POST /perfil/agent-token` — session-authenticated, handled by `AgentTokenController`.

### Agent connection flow

1. User starts the agent with `--tray` — the system tray menu only shows **Conectar** and **Cerrar**
2. User clicks **Conectar** — a tkinter dialog appears asking for the token
3. User pastes the token and clicks **Guardar**
4. Agent calls `GET /api/agent/me` with `Authorization: Bearer <token>` to validate
5. Backend returns `{ id, email, name, firstName }` — the agent shows a confirmation card
6. Token and user info are persisted in `~/.pideinfo-agent/preferences.json`
7. The tray menu switches to the full connected state

### Connected menu

Once connected, the system tray menu shows:

```
Sincronizar ahora
Resetear
───────────────────
Aceptar notificaciones electrónicas
───────────────────
Desconectar
Conectado como user@example.com
───────────────────
Cerrar
```

### API endpoints

All endpoints under `/api/agent/` are protected by the `api` firewall in `security.yaml`, which uses JWT authentication and the same `UserChecker` as the web firewall (inactive users are rejected even with a valid token).

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/api/agent/me` | GET | Validate token, return user info |
| `/api/agent/webhook` | POST | Receive documents from the agent |

Both are rate-limited to 60 requests/minute per IP (the `AGENT` rate limiter in `config/packages/rate_limiter.yaml`).

### Legacy webhook

The old endpoint `POST /webhook/agent` with `X-Webhook-Secret` header authentication remains functional for backward compatibility. It is handled by `AgentController` and delegates processing to the same `AgentWebhookProcessor` service.

## Execution modes

| Flag | Mode | Description |
|------|------|-------------|
| `--tray` | System tray | Menu bar icon with sync controls. Requires `pystray` and `Pillow`. |
| `--once` | Single sync | One sync cycle, then exit |
| `--daemon` | Periodic | Sync on a schedule (default: every 30 min via APScheduler) |
| `--auth-only` | Auth test | Authenticate against the portal and exit |
| `--dry-run` | Preview | Scrape portal but don't send anything to PideInfo |
| *(none)* | Default | Same as `--once` |

All modes accept `--env-file <path>` to specify a custom `.env` file (default: `.env`).

## Configuration

Settings are loaded from environment variables and/or a `.env` file via `pydantic-settings`.

| Variable | Default | Description |
|----------|---------|-------------|
| `PIDEINFO_BASE_URL` | `http://localhost:8000` | PideInfo server URL (used for JWT auth) |
| `PORTAL_URL` | `https://transparencia.sede.gob.es` | Portal de Transparencia URL |
| `PORTAL_CTBG` | `https://sede.consejodetransparencia.gob.es/info.0` | CTBG sede electrónica URL |
| `AUTH_TIMEOUT_SECONDS` | `120` | Browser auth timeout |
| `SYNC_INTERVAL_MINUTES` | `30` | Daemon mode sync interval |
| `DATA_DIR` | `~/.pideinfo-agent` | Directory for cookies, state, preferences, downloads |
| `CLIENT_CERT_P12` | *(none)* | Path to FNMT certificate (.p12) for auto-selection |
| `CLIENT_CERT_PASSPHRASE` | *(none)* | Certificate passphrase |

Legacy variables (`PIDEINFO_WEBHOOK_URL`, `PIDEINFO_WEBHOOK_SECRET`, `PIDEINFO_USER_ID`) are still supported for backward compatibility but deprecated in favor of JWT authentication.

## Portal authentication

The Portal de Transparencia uses Spain's Cl@ve identity system. The agent authenticates using a headed Playwright browser that allows the user to select their FNMT digital certificate:

1. Playwright opens the portal login page
2. The portal redirects to Cl@ve, which presents certificate selection
3. If `CLIENT_CERT_P12` is set, the browser auto-selects the certificate
4. The user may need to enter their certificate passphrase
5. After authentication, the agent captures the session cookies
6. Cookies are persisted to `~/.pideinfo-agent/cookies.json` and reused until expired (validated by hitting `/privada/expedientes`)
7. Cookies are considered stale after 4 hours but are still validated before re-authentication

If a session expires mid-sync, the agent catches the redirect to Cl@ve and raises `SessionExpiredError`.

## Sync cycle

A single sync cycle (`do_sync`) performs:

1. **Authenticate** — load saved cookies or trigger browser auth
2. **Scrape expedientes** — fetch the user's FOIA requests from the portal
3. **Scrape notificaciones** — fetch notifications (responses, extensions, etc.)
4. **Sync expediente documents** — for each expediente, fetch its document list, download new ones, send as a batch to PideInfo. `SOLICITUD` documents are sorted first so the batch handler can create the `AccessRequest` with correct metadata.
5. **Sync notification documents** — download and send each new notification's document. If a notification was `PENDIENTE` and is now downloaded, the agent marks it as accepted.
6. **Report pending notifications** — inform PideInfo about `PENDIENTE` notifications without downloading them (so PideInfo can show a banner). Sends an empty list to clear notifications that have been resolved.
7. **Sync CTBG notifications** — authenticate against the CTBG sede electrónica (separate session), scrape the notification list from `/enotifications.9`, report any `Pendiente` notifications to PideInfo (source: `consejo_ctbg`). Non-fatal if auth fails. First page only (Wicket AJAX pagination not supported).
8. **Save state** — mark synced documents in `~/.pideinfo-agent/sync_state.json`

### Deduplication

The agent tracks synced documents by `(id_expediente, id_documento)` in its local state file. The backend also deduplicates by `contentHash` (SHA-256 of file content) per user, so re-syncing the same document is safe.

### Pending notifications

Some notifications require the user to formally accept (*comparecer*) them on the portal before they can be downloaded. The agent handles this in two ways:

- **Auto-accept disabled** (default): The agent reports `PENDIENTE` notifications to PideInfo without downloading them. PideInfo shows a banner on the affected access request.
- **Auto-accept enabled** (via tray menu toggle): The agent downloads `PENDIENTE` notifications, which constitutes accepting them. This feature is behind the `ACCEPT_NOTIFICATIONS_AVAILABLE` flag and is currently disabled until the comparecencia endpoint is implemented in the scraper.

## Webhook payload format

The agent sends JSON payloads to the webhook endpoint. Three payload types:

### Document sync

```json
{
    "source": "transparencia_age",
    "expedienteRef": "R/0123/2025",
    "documents": [
        {
            "filename": "RESOLUCIÓN - R/0123/2025.pdf",
            "contentType": "application/pdf",
            "content": "<base64>",
            "contentHash": "<sha256>"
        }
    ],
    "metadata": {
        "notificationId": 12345,
        "notificationType": "RESOLUCIÓN",
        "expedienteId": 67890,
        "fechaEmision": "2025-03-15"
    }
}
```

When using legacy auth, the payload includes `"userId": "<uuid>"`. With JWT auth, the user is derived from the token.

### Pending notifications report

```json
{
    "source": "transparencia_age",
    "expedienteRef": "R/0123/2025",
    "documents": [],
    "pendingNotifications": [
        {
            "notificationId": 12345,
            "tipo": "RESOLUCIÓN",
            "concepto": "...",
            "fechaEmision": "2025-03-15",
            "fechaCaducidad": "2025-03-25",
            "esComunicacion": false
        }
    ],
    "metadata": { "expedienteId": 67890 }
}
```

### CTBG pending notifications report

```json
{
    "source": "consejo_ctbg",
    "expedienteRef": "666/2026",
    "documents": [],
    "pendingNotifications": [
        {
            "notificationId": "2026-S-RE-3781",
            "tipo": "Notificación Electrónica",
            "concepto": "",
            "fechaEmision": "30/03/2026 11:48",
            "fechaCaducidad": null,
            "esComunicacion": false
        }
    ],
    "metadata": {}
}
```

The `expedienteRef` matches `AccessRequestComplaint.externalId` in PideInfo. The backend's `findByExternalId` method also searches complaint external IDs.

Each stored notification is enriched server-side with a `reportedAt` timestamp (ISO 8601) and the `source` field (`transparencia_age` or `consejo_ctbg`). The UI renders Portal de Transparencia and Consejo de Transparencia notifications in separate, visually distinct sections.

### Accepted notification

Same as document sync, with an additional `acceptedNotifications` or `acceptedCommunications` array containing the metadata of the notifications that were downloaded (and thus accepted) by the agent.

## System tray

The tray icon uses `pystray` (cross-platform) with a `Pillow`-drawn icon:
- **Blue circle** at rest
- **Amber circle** while syncing
- Stylized "P" letter inside

Platform-specific behavior:
- **macOS**: Hides from Dock via `NSApplicationActivationPolicyAccessory`. Icon appears in the menu bar.
- **Windows**: Hides console window via `ShowWindow(hwnd, SW_HIDE)`. Icon appears in the system tray.
- **Linux**: Uses AppIndicator API (requires `libayatana-appindicator`).

Threading model: the tray icon owns the main thread (macOS requirement). An asyncio event loop runs in a background daemon thread, and sync operations are dispatched via `asyncio.run_coroutine_threadsafe()`. UI dialogs (tkinter) run on the main thread via the tray callbacks.
